1. PURPOSE AND SCOPE

Orion, then notify the supplied recipient after access is verified.
Only backend/src/api/main.py was edited among existing tracked source files.

3. EXISTING MAIL FLOW AND THE INTEGRATION DECISION

Existing core/mailing/mailer.py renders templates from the adjacent templates
directory. It escapes template inputs. SMTP uses the existing internal relay
via smtplib.SMTP; it currently does not use authentication or STARTTLS.
Existing approval/result emails use the outbox worker in worker/jobs/mail.py.
Existing batch-key operations also call the shared mailer directly.

This new admin operation follows the direct-mail pattern. There is NO new
outbox job, durable mail retry, migration or worker registration. After a
verified grant it attempts mail synchronously before returning HTTP 200.
If mail fails, the response still states the actual grant status and includes
notification.status=failed. Retry the same endpoint to retry the notification:
it will recheck access, skip /key/update if already granted, and send again.
Repeated successful calls can therefore produce duplicate notifications.
SMTP acceptance is not proof of delivery into the user's inbox.

5. API CONTRACT AND MANUAL CALL

Direct backend URL: POST /admin/grant-mcp
Through existing Nginx: POST /api/admin/grant-mcp
Authorization: Bearer <ORION_SUPERUSER_ACCESS_TOKEN>
This is the Orion login JWT, NOT the LiteLLM master key.
Content-Type: application/json

Request example (replace alias/server with real values):
{
  "key_alias": "ALZ-BRYSL-EXISTING-KEY",
  "mcp_name": "existing-mcp-server-name",
  "environment": "PROD",
  "recipient_email": "extern.hamza-hacioglu@allianz.com.tr"
}

HTTP 200 example:
{
  "status": "granted",
  "key_alias": "ALZ-BRYSL-EXISTING-KEY",
  "mcp_name": "existing-mcp-server-name",
  "mcp_server_id": "resolved-server-id",
  "environment": "PROD",
  "models": [],
  "notification": {
    "status": "smtp_accepted",
    "recipient_email": "extern.hamza-hacioglu@allianz.com.tr"
  }
}

status can also be already_granted. notification.status is:
  smtp_accepted: existing mailer completed its SMTP send without an exception.
  recorded: local placeholder/mailbox only; NO email was sent.
  failed: grant succeeded but notification failed; investigate SMTP and retry.

Errors: authentication 401; non-admin or alias policy 403; missing key/server
404; ambiguous lookup 409; invalid/missing body fields 422; upstream/network/
verification failure 502; missing LiteLLM configuration 503.
Grant errors do not trigger success mail. A network/verification error AFTER
/key/update can mean access changed but was not confirmed; inspect LiteLLM
before retrying. No rollback/revocation is attempted.

8. OPERATIONAL NOTES AND ROLLBACK

Keep updates to the SAME virtual key serialized across admin tools/services:
LiteLLM's read/merge/update sequence does not provide an atomic permission
append, so concurrent writers can overwrite each other's changes. This
integration, like the standalone version, does not add cross-process locking.
The server list and alias-filtered key list use the same provider endpoints
and response shapes as the known-working standalone implementation.

To roll back the code, remove the two grant_mcp registration lines from
backend/src/api/main.py and redeploy backend-api. Unreferenced feature files
can then be removed. Code rollback does NOT revoke grants already made and
does not undo sent emails. Handle revocation separately through the normal
LiteLLM administration process if required.
